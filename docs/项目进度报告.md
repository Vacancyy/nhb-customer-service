# 宁惠保智能客服项目进度报告

## 项目概述

宁惠保智能客服是一个基于 Next.js 全栈应用构建的 AI 保险客服系统，支持 RAG（检索增强生成）、意图插件路由、短信实名认证和多轮对话。

---

## 技术选型与设计决策

### 为什么选择 Next.js？

**问题背景**：
- 项目需要一个完整的全栈解决方案，包含前端界面、后端 API、数据库操作
- 需要快速开发和部署
- 团队熟悉 React 生态

**选择 Next.js 的原因**：

| 特性 | 说明 |
|------|------|
| 全栈一体 | 前端页面 + 后端 API 在同一项目，无需拆分 |
| App Router | 新的路由系统，支持 React Server Components |
| TypeScript | 类型安全，开发体验好 |
| TailwindCSS | 快速样式开发，无需手写 CSS |
| 部署简单 | standalone 输出，单容器部署 |

**遇到的问题与解决方案**：

| 问题 | 解决方案 |
|------|----------|
| API 路由 basePath 配置 | 在 `next.config.mjs` 设置 `basePath: '/nhb-customer-service'` |
| SSE 流式响应跨域 | 使用相对路径 API 调用，避免 CORS 问题 |
| 动态导入第三方库 | 使用 `import('eruda')` 动态加载，避免 SSR 报错 |
| 环境变量区分 | `.env.local` 本地开发，`.env.stage` 线上测试 |

---

### 为什么选择 PostgreSQL + pgvector？

**问题背景**：
- 需要存储知识库数据并进行语义相似度搜索
- 知识库数据量约千级，不是大规模向量检索场景
- 团队希望避免引入额外的向量数据库（如 Milvus、Pinecone）

**选择 pgvector 的原因**：

| 优势 | 说明 |
|------|------|
| 统一数据库 | 向量数据和业务数据在同一数据库，无需维护多个系统 |
| 成熟稳定 | PostgreSQL 已有成熟的运维体系 |
| 性能足够 | IVFFlat 索引支持，千级数据检索毫秒级响应 |
| 成本低 | 无需额外购买向量数据库服务 |

**遇到的问题与解决方案**：

| 问题 | 解决方案 |
|------|----------|
| ORM 不支持 VECTOR 类型 | 使用原生 SQL（pg 驱动），不用 Prisma/Sequelize |
| 向量维度固定 | 选择 OpenAI embedding-3-small（1536维），通用性强 |
| 索引选择 | IVFFlat 索引适合中等数据量，lists 参数根据数据量调整 |
| 中文语义搜索 | 使用阿里 DashScope 或 OpenAI embedding，对中文支持良好 |

**向量检索 SQL 示例**：
```sql
SELECT std_question, answer
FROM knowledge_entries ke
JOIN knowledge_answers ka ON ke.id = ka.knowledge_id
ORDER BY ke.embedding <=> $1  -- 余弦距离
LIMIT 3;
```

### 为什么选择 Redis？

**问题背景**：
- 需要存储会话历史、验证码、用户认证状态
- 需要实现动态配置开关，实时生效

**Redis 的用途**：

| 用途 | Key 格式 | TTL | 说明 |
|------|----------|-----|------|
| 会话历史 | chat_history:{userId}:{channel} | 7天 | 多轮对话上下文 |
| 认证缓存 | user_auth_cache:{userId} | 24小时 | 用户实名认证信息 |
| 验证码 | verify_code_a/b:{phone} | 5分钟 | 短信验证码 |
| 配置开关 | system_config:{key} | 永久 | 审核开关等配置 |

**为什么用 Redis 存储会话历史而不是数据库**？

| 考量 | Redis | PostgreSQL |
|------|-------|------------|
| 读写性能 | 微秒级 | 毫秒级 |
| TTL 自动过期 | 支持 | 需定时清理 |
| 数据结构 | List 自然支持消息列表 | 需要 JSON 字段 |
| 用途 | 临时会话数据 | 审计日志存储 |

**遇到的问题与解决方案**：

| 问题 | 解决方案 |
|------|----------|
| 线上 Redis 是 Sentinel 模式 | ioredis 支持 Sentinel 连接，配置 sentinels 数组 |
| 密码特殊字符 | 确保 password 参数正确传递，避免 URL 解析问题 |
| Key 前缀管理 | 定义 REDIS_KEY_PREFIX 常量，统一管理 |

---

### 为什么选择阿里 DashScope？

**问题背景**：
- 需要国产 LLM，数据不出境
- 成本敏感，需要性价比高的模型
- 需要支持中文保险领域问答

**选择 qwen 系列的原因**：

| 特性 | 说明 |
|------|------|
| 国产合规 | 数据在国内处理，符合数据安全要求 |
| 中文能力强 | qwen 对中文理解优于同级别国外模型 |
| 成本低 | qwen-plus 价格约 GPT-4 的 1/10 |
| OpenAI 兼容 API | 可直接使用 OpenAI SDK，无需改动代码 |

**遇到的问题与解决方案**：

| 问题 | 解决方案 |
|------|----------|
| 流式响应格式 | DashScope SSE 格式与 OpenAI 一致，直接解析 |
| 工具调用支持 | qwen 支持 function calling，与 OpenAI 格式兼容 |
| 模型版本选择 | qwen-plus 日常使用，qwen-max 复杂场景 |

### 为什么实现审核功能？

**问题背景**：
- AI 生成的内容可能不准确或不合适
- 保险行业对信息准确性要求高
- 需要人工把关确保服务质量

**审核流程设计考量**：

1. **为什么生成后审核，而不是生成前限制？**
   - 生成后审核不影响用户体验（后台生成）
   - 可以收集 AI 生成错误数据，改进模型
   - 管理员可以编辑回答，纠正错误

2. **为什么用 Redis 开关控制审核？**
   - 实时生效：修改后立即对所有请求生效
   - 无需重启：服务正常运行，开关独立
   - 运维友好：管理员可自行操作，无需开发介入

3. **为什么设置超时自动处理？**
   - 避免用户长时间等待
   - 管理员不在时系统仍能响应
   - 默认回答："抱歉，AI回答生成失败..."

---

### 技能/插件系统设计

**问题背景**：
- 不同业务场景需要不同处理逻辑
- 知识库问答、订单查询、理赔查询各有特点
- 需要可扩展架构，方便添加新功能

**设计思路**：

```
用户消息
    │
    ▼
LLM 意图路由
    │
    ├── "报销流程" ──► knowledge_query 技能
    ├── "查询保单" ──► order_query 技能（需认证）
    ├── "理赔进度" ──► claim_query 技能（需认证）
    │
    ▼
技能执行
    │
    ▼
结果返回给 LLM
    │
    ▼
生成最终回答
```

**为什么用 Agent Loop 模式？**

| 传统单次调用 | Agent Loop |
|-------------|------------|
| 单次请求-响应 | 多轮工具调用 |
| 无法处理复杂查询 | 可链式调用多个技能 |
| 回答固定 | 根据技能结果动态生成 |

**Agent Loop 最大迭代次数限制为 5，避免无限循环消耗资源。**

### 3. 审核开关控制

**功能描述**：通过管理界面实时控制审核功能的启用/禁用

**实现路径**：
- API: `/api/admin-api/config/switch`
- 界面: `/web/admin/review` 顶部栏

**核心特性**：
- Redis 存储开关状态（`system_config:review_enabled`）
- 实时生效，无需重启服务
- 可视化开关按钮

**设计思路**：

**为什么用 Redis 控制开关？**

| 方式 | 优点 | 缺点 |
|------|------|------|
| 代码硬编码 | 简单 | 需要重新部署才能修改 |
| 配置文件 | 不需要改代码 | 需要重启服务 |
| 数据库 | 动态修改 | 需要数据库查询，性能开销 |
| **Redis** | **实时生效、无重启、高性能** | 需要 Redis 服务 |

**实现逻辑**：

```typescript
// check-status API 核心逻辑
const reviewEnabledValue = await redisClient.get('system_config:review_enabled');
const reviewEnabled = reviewEnabledValue === 'true' || reviewEnabledValue === '1';

if (!reviewEnabled) {
  // 审核禁用，直接返回数据
  return { status: 'success', output: record.output, reviewBypassed: true };
}

// 审核启用，根据实际状态返回
if (record.status === 'pending') {
  return { status: 'pending', message: '正在审核中' };
} else if (record.status === 'success') {
  return { status: 'success', output: record.output };
} else if (record.status === 'rejected') {
  return { status: 'rejected', message: '审核未通过' };
}
```

## 关键技术决策

### 1. 为什么选择 pgvector 而不是专用向量数据库？

- PostgreSQL 已有成熟的运维体系
- pgvector 性能满足当前需求（千级数据量）
- 避免引入额外数据库，降低运维复杂度

### 2. 为什么审核功能用 Redis 开关控制？

- 实时生效：修改开关后立即对所有请求生效
- 无需重启：不影响服务运行
- 运维友好：管理员可直接操作，无需开发介入

### 3. 为什么用 SSE 流式响应？

- 用户感知响应更快
- 减少长请求的等待焦虑
- 支持大模型生成的实时展示
